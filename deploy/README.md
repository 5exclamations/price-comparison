# Развёртывание

Один VPS, docker-compose, терраформ-модуль под машину. Kubernetes не ставим:
сервисов пять, машина одна, а оркестратор — это ещё одна вещь, которую надо
чинить в три часа ночи.

```
deploy/
  docker-compose.yml       пять сервисов + бэкапы
  caddy/Caddyfile          TLS сам, наружу только 80/443
  docker/                  образы api, worker, backup + расписания
  scripts/                 прогон сбора, бэкап, откат, сторож, первый запуск
  terraform/               машина, диск, файрвол, cloud-init
  .env.example             секреты; заполненный файл не коммитить
```

## Развернуть с нуля

```bash
cd deploy/terraform
export HCLOUD_TOKEN=...
terraform init
terraform apply -var domain=api.qiymet.az -var repo_url=git@github.com:...
```

Дальше терраформ печатает адрес. **Прописать A-запись до первого старта Caddy**:
сертификат выпускается проверкой по HTTP-01, и без записи домен не подтвердится.

```bash
ssh qiymet@<адрес>
cd /srv/qiymet/deploy
cp .env.example .env && $EDITOR .env      # пароль базы, домен, телеграм
./scripts/first-run.sh
```

`first-run.sh` идёт по шагам и останавливается на первом же провале. Он делает
миграции, первый полный сбор (около часа: `full` тянет штрихкоды по одному),
перелив в Postgres, проверки данных, первый прогон уведомлений и первый бэкап
с проверкой отката.

Секреты через терраформ **не** передаются. Всё, что попадает в переменные
терраформа, попадает и в state, а state однажды оказывается в репозитории.

## Что из этого проверено, а что нет

Проверено по-настоящему, на живой базе и в контейнерах:

* три образа собираются (`api`, `worker`, `backup`), оба расписания
  supercronic принимает как валидные;
* контейнер API отвечает на `/healthz`, `/v1/health` и `/v1/search` против
  настоящих Postgres и Redis; ETag отдаётся, повтор с `If-None-Match` даёт 304;
* весь набор тестов API (163 штуки) прошёл против **настоящего** Redis, а не
  fakeredis;
* `backup.sh` снял дамп 4.4 МБ, `restore-test.sh` развернул его на пустую базу
  за 2 с (36 214 товаров, 57 459 наблюдений) и пересобрал витрины;
* обрезанный дамп проверка отката отвергает с кодом 1;
* сторож ловит все три своих случая: протухшие сети с часами по каждой, «за
  сутки ни одного наблюдения», «наблюдения есть, изменений цены ноль».

Не проверено, и вот почему:

* **`terraform apply` не запускался** — нет ни токена Hetzner, ни желания
  создавать платную машину. Синтаксис модуля не проверен `terraform validate`:
  terraform на машине не установлен;
* **Caddy с настоящим TLS** — сертификат выпускается только на живой домен
  с A-записью;
* **FCM против настоящего Google** — нет сервисного аккаунта, проекта Firebase
  и токена устройства. Для этого написан `scripts/fcm-smoke.py`, см. ниже;
* **первый прогон сбора по расписанию** — по определению проверяется только
  после деплоя.

### Проверка FCM

```bash
export QIYMET_FCM_PROJECT_ID=qiymet-test
export GOOGLE_APPLICATION_CREDENTIALS=/path/fcm-service-account.json
python3 deploy/scripts/fcm-smoke.py --token '<токен устройства>'
```

Скрипт шлёт настоящий пуш, потом заведомо мёртвый токен, потом запрос с битым
OAuth — и печатает таблицу «ждали / получили». Проверяется ровно то, чего не
проверяют моки: что `classify()` в `notify/fcm.py` называет ответы настоящего
Google теми же словами, что и `CollectingFcm` в тестах.

Самый важный случай в этой таблице — 401. Если протухшая учётка **сервера**
уедет в `DEAD_TOKEN`, мы разом выключим токены всех пользователей, и вернуть
их нельзя: приложение перерегистрирует токен только при переустановке.

Проект брать тестовый, а не боевой: скрипт шлёт настоящий пуш, и на боевом он
прилетит живому человеку. Скрипт сам отказывается работать, если в имени
проекта есть `prod`.

## Расписание

Оно живёт в `docker/crontab` и едет вместе с образом. Cron хоста не
используется намеренно: он ничего не знает про образ и после обновления
продолжит звать вчерашний код.

| когда | что |
|---|---|
| каждые 3 часа | `fast`: цены и акции, ~4 минуты |
| 4:15 | `full`: плюс новые товары и штрихкоды |
| понедельник 5:30 | перезамер ценовых зон Bravo |
| каждые 15 минут | отправка накопленных уведомлений |
| каждый час | сторож: возраст данных, проверки, дельты |
| 3:30 | бэкап |
| 1-го в 5:00 | проверка восстановления |

### Порядок внутри прогона

```
ensure_price_partitions_ahead(3)
  -> run.py fast|full          (пишет в SQLite; выпавшая точка = ненулевой код)
  -> db/import_sqlite.py       (SQLite -> Postgres)
  -> import_sqlite.py --verify (сверка счётчиков ДО витрин)
  -> refresh_after_crawl()     (current_prices, затем deal_honesty)
  -> checks.runner --source crawl
  -> notify run
```

Порядок не декоративный, каждый шаг стоит там, где стоит, по конкретной
причине:

**Секции перед сбором.** Иначе первого числа месяца наблюдения пойдут в секцию
DEFAULT. Данные не потеряются, но уедут в общую кучу, и заметить это можно
будет только по вьюхе `price_partitions_health` — то есть если специально
пойти и посмотреть.

**Перелив отдельным шагом.** Пайплайн пишет в SQLite, а не в Postgres. Без
перелива все следующие шаги отработают по вчерашним данным и бодро отрапортуют
об успехе.

**`refresh_after_crawl()` перед `notify`.** Воркер уведомлений читает
`deal_honesty`. Со вчерашней витриной он не отличит накрученную скидку от
настоящей и отправит ровно то, что обещал не отправлять — «было 5 ₼, стало
3 ₼» на товаре, который в соседней сети всегда стоил 3 ₼.

**Сверка счётчиков перед витринами, а не после.** Оборванный перелив — сеть
моргнула, кончилось место, процесс убили по OOM — раньше доводил дело до конца
так: витрины пересобирались по неполным данным, а расхождение счётчиков
печаталось уже после. Половина каталога в `current_prices` не выглядит аварией:
у товара просто «нет цены в этой сети», и уведомления уходят по падениям,
которых не было. Теперь при расхождении витрины не трогаются вовсе — в базе
остаются прежние, старые, но целые.

**Выпавшая точка роняет прогон.** `VENUES` в `pipeline/run.py` — это
конфигурация, а не пожелание. Недоступная точка или точка, отклонённая
проверкой медианной цены, даёт ненулевой код возврата и список выпавших.
Раньше `run.py` печатал «ПРОПУЩЕН <slug>» и заканчивался нулём, а цепочка шла
дальше как ни в чём не бывало.

**Проверки данных перед уведомлениями.** Если сбор привёз мусор, пуши по нему
не уходят. Упавшие проверки прогон не останавливают: результат уже записан
в `dq_runs`, приложение показывает плашку, а рассылку мы придерживаем.

**`--source crawl` и БЕЗ `--allow-stale`.** Флаг существует только для CI, где
база поднимается из дампа в репозитории и заведомо несвежая. На проде проверка
возраста — главная: она ловит сеть, переставшую обновляться. Раннер
отказывается принимать `--allow-stale` вместе с `--source crawl`, чтобы это
нельзя было сделать по невнимательности.

## Мониторинг

Три уровня, и они отвечают на разные вопросы.

**1. Внешний uptime-монитор** — UptimeRobot, BetterStack, healthchecks.io,
любой. Отвечает на вопрос «жив ли сервис снаружи».

```
URL:      https://api.qiymet.az/v1/health
интервал: 5 минут
ключевое слово: "status":"ok"   (должно ПРИСУТСТВОВАТЬ)
уведомления: Telegram
```

Ключевое слово важнее самого кода ответа. `/v1/health` отдаёт 200 и когда всё
плохо: `status` становится `degraded`, если сеть не обновлялась дольше 12 часов
или последний прогон проверок данных упал. Монитор, смотрящий только на код
ответа, не увидит ни того, ни другого.

**2. Пульс изнутри.** Монитор, который спрашивает наш API, узнает про упавший
API. Про то, что **встало расписание**, он не узнает никогда: API продолжит
бодро отдавать вчерашние цены. Поэтому `run-crawl.sh` после полного прохода
всех шагов дёргает `HEARTBEAT_URL_CRAWL`. Молчание само по себе становится
сигналом.

```bash
# в .env
HEARTBEAT_URL_CRAWL=https://hc-ping.com/<uuid>
```

Период на стороне монитора — 4 часа с запасом (сбор каждые 3).

**3. Сторож внутри.** `watchdog.sh` раз в час смотрит то, чего снаружи не
видно, и пишет в телеграм:

* **точка** не обновлялась дольше 12 часов — с именами точек и часами. Именно
  точка, а не сеть: сбор молча переживает потерю одного магазина, и у Bravo
  с четырьмя ценовыми зонами по сети это не видно вовсе;
* последний прогон проверок данных упал — с именами упавших проверок;
* проверки не запускались дольше 4 часов — значит встало расписание;
* **за сутки ноль изменений цены** при непустом сборе.

Последнее — про то, чего ещё ни разу не было. Пайплайн до сих пор не работал
по расписанию: истории цен нет, она начинает копиться только сейчас. Сбор,
который исправно пишет наблюдения, но ни одно из них не отличается от
предыдущего, выглядит абсолютно здоровым: возраст данных свежий, проверки
проходят, в логах пусто. А продукта нет — сравнивать нечего.

Проверка включается со **вторых** суток: в первые сравнивать не с чем по
определению, и алерт был бы ложным ровно один раз — сразу после деплоя, когда
его меньше всего хотят видеть.

## Логи

В файлах на хосте, `deploy/logs/`, не в stdout контейнера. Через `docker logs`
история теряется при пересоздании контейнера, а грепать её нечем.

```
logs/pipeline/crawl-fast.log     прогон сбора целиком, по шагам
logs/pipeline/crawl-full.log
logs/pipeline/zones.log          перезамер зон Bravo
logs/pipeline/notify.log         отправка уведомлений
logs/pipeline/watchdog.log       ежечасный сторож
logs/backup/backup.log
logs/backup/restore-test.log
logs/caddy/access.log
```

Ротация — своя, в `lib.sh`: 20 МБ на файл, 5 файлов. Logrotate в контейнере был
бы ещё одним демоном ради пяти файлов. У контейнеров дополнительно стоит
`json-file` с теми же лимитами: место на VPS кончается тихо, а кончившееся
место роняет Postgres.

## Бэкапы

Ежедневно в 3:30 — **до** ночного полного прогона, чтобы откатываться было на
состояние до него. `pg_dump -Fc`: сжат и позволяет достать одну таблицу, не
разворачивая всю базу.

Хранение 30 дней. Проверка отката — первого числа в 5:00, автоматическая, на
пустую базу. Бэкап, который ни разу не разворачивали, — это не бэкап, а надежда.

Проверяется не только «`pg_restore` не упал»: он не падает и на дампе, где
половина таблиц пустые. После отката считаются строки в главных таблицах и
вызывается `refresh_after_crawl()` — витрины строятся из данных, и если данные
битые, ошибка вылезет именно там.

Результат проверки уходит в телеграм **и при успехе тоже**. Молчащий мониторинг
неотличим от сломанного: раз в месяц увидеть «откат проверен» стоит дешевле,
чем однажды обнаружить, что проверка не запускалась полгода.

Ручной откат:

```bash
docker compose stop api worker
docker compose exec -T postgres psql -U qiymet -d postgres \
  -c "DROP DATABASE qiymet" -c "CREATE DATABASE qiymet TEMPLATE template0 ENCODING 'UTF8' LC_COLLATE 'C' LC_CTYPE 'C'"
docker compose exec -T postgres pg_restore -U qiymet -d qiymet --no-owner /backups/qiymet-2026-08-17.dump
docker compose exec -T postgres psql -U qiymet -d qiymet -c "SELECT refresh_after_crawl()"
docker compose start api worker
```

# Когда сеть поменяет витрину

Это вопрос не «если», а «когда». Пять из шести сетей отдают данные через Wolt,
и мы у них ничего не спрашивали: всё, что делает пайплайн, — это скрейпинг
чужой витрины. Ни одна из сетей не обязана предупреждать нас об изменениях,
и ни одна не будет.

## Как выглядит поломка

По убыванию частоты и по возрастанию неприятности.

**1. Коннектор упал с ошибкой.** Лучший случай: видно сразу. Прогон падает,
в телеграм приходит «Сбор (fast) упал», в логе — трассировка. Цены в базе
остаются вчерашние, приложение показывает время последней проверки честно.

**2. Коннектор вернул пусто.** Wolt поменял эндпоинт и отвечает 410 либо
пустым ассортиментом. Ошибки нет, сбор «прошёл». Ловит проверка 8: возраст
данных сети перевалит за 12 часов, `/v1/health` уйдёт в `degraded`, сторож
напишет в телеграм.

**3. Коннектор вернул мусор.** Самый неприятный случай, и он уже случался.
Слаг `grandmart` выглядел как бакинский магазин, отдавал 596 товаров и
грузился без единой ошибки — но это была русскоязычная точка другой страны
с медианной ценой 1014 против 1.4–4.4. Формально данные валидные, по сути
мусор. Ловит проверка 5 (медиана цены сети вне 0.30–50 ₼).

**4. Поменялась разметка полей.** Витрина стала отдавать `original_price`
там, где раньше был `price`, или потеряла `barcode_gtin`. Цены остаются
правдоподобными, а вот скидки и склейки едут. Ловят проверки 2 (акция, где
цена выросла), 4 (развалившаяся склейка) и 6 (просевший разбор фасовки —
и по каждой сети отдельно, а не только по базе целиком).

**5. Ничего не сломалось, но и не поменялось.** Сеть заморозила витрину
или отдаёт кеш. Сбор пишет, возраст свежий, проверки проходят. Ловит только
сторож дельт: ноль изменений цены за сутки при непустом сборе.

## Что делать

### Шаг 1. Понять, какая сеть и что именно

```bash
# Возраст данных по сетям — то же, что видит приложение.
docker compose exec postgres psql -U qiymet -d qiymet -c "
  SELECT c.code,
         max(cp.observed_at) AS последнее,
         round(extract(epoch FROM now() - max(cp.observed_at))/3600, 1) AS часов,
         count(*) AS позиций
  FROM chains c
  JOIN store_items si ON si.chain_id = c.id
  JOIN current_prices cp ON cp.store_item_id = si.id
  GROUP BY c.code ORDER BY 3 DESC"

# Последний прогон проверок: что именно упало и с какими нарушителями.
docker compose exec postgres psql -U qiymet -d qiymet -c "
  SELECT started_at, passed, jsonb_pretty(failures)
  FROM dq_runs ORDER BY started_at DESC LIMIT 1"

# Лог прогона: там пошагово видно, докуда дошло.
tail -100 deploy/logs/pipeline/crawl-fast.log
```

### Шаг 2. Проверить руками, что отдаёт сеть

Wolt (Bravo, Araz, SPAR, Neptun, Rahat):

```bash
curl -s -H 'platform: Web' -H 'clientversionnumber: 1.13.16' \
  'https://consumer-api.wolt.com/consumer-api/consumer-assortment/v1/venues/slug/<venue>/assortment' \
  | head -c 2000
```

Без заголовков `platform` и `clientversionnumber` прилетит 410, и это НЕ
поломка витрины, а наш забытый заголовок.

Bazarstore (Shopify):

```bash
curl -s 'https://bazarstore.az/products.json?limit=5' | head -c 2000
curl -s 'https://bazarstore.az/collections/endirimli-mehsullar/products.json?limit=5' | head -c 2000
```

Акции лежат во второй коллекции: в общем фиде `compare_at_price` заполнен
только у 10.8% вариантов.

### Шаг 3. Решить, чинить сейчас или отключить сеть

**Отключить — нормальное решение.** Приложение переживает отсутствие одной
сети: `chains_count` уменьшится, лучшая цена посчитается по остальным. Чего
приложение не переживает — это показ неверной цены как верной.

```sql
-- Сеть перестаёт участвовать в выдаче, данные остаются на месте.
UPDATE chains SET active = 0 WHERE code = 'neptun';
SELECT refresh_after_crawl();
```

Чинить в спешке ночью хуже, чем показать пять сетей вместо шести.

### Шаг 4. Починить коннектор

Правило, из-за которого этот раздел вообще написан отдельно: **починка
коннектора не считается законченной, пока не пройдены проверки данных.**

```bash
# 1. Прогон в сторону от боевой базы.
cd pipeline && QIYMET_SQLITE=/tmp/probe.db python3 run.py fast

# 2. Посмотреть глазами, что приехало: медиана цены — первый признак.
sqlite3 /tmp/probe.db "
  SELECT c.code, count(*), round(avg(s.price)/100.0, 2)
  FROM store_items si JOIN chains c ON c.id = si.chain_id
  JOIN prices s ON s.store_item_id = si.id GROUP BY c.code"

# 3. И только потом на боевую.
deploy/scripts/run-crawl.sh fast
```

Проверка 5 (медиана вне 0.30–50 ₼) не зря стоит первой в этом списке: именно
она отличает «сеть переехала на новый эндпоинт» от «сеть переехала в другую
страну».

### Шаг 5. Занести случай в проверки

Если поломка прошла мимо всех восьми проверок — значит проверок восемь, а
должно быть девять. Новая проверка пишется в `checks/data_checks.py` по тому
же правилу: **возвращать нарушителей, а не их количество**. Дежурному в три
часа ночи нужно `neptun/30013586 цена 0`, а не «1 строка».

## Чего делать не надо

**Не подкручивать пороги, чтобы проверка позеленела.** Порог 0.30–50 ₼ взят
не с потолка: медианы наших шести сетей лежат в 2.89–6.60 ₼, а у чужой точки
было 1014 ₼. Расширив диапазон, вы не почините сеть — вы выключите проверку.

**Не выводить ценовые зоны Bravo из названия магазина.** Зона — измеренное
поле `stores.price_cluster`. В одной зоне лежат Superstore, Supermarket и
Ekspress с ценами до копейки одинаковыми; в разных зонах — два Superstore
с разными. Название не говорит о зоне ничего.

**Не показывать цену сети, у которой прайс зависит от магазина, без
выбранного магазина.** Это не осторожность, это единственный способ не
соврать: у Bravo четыре разных прайса, и любой из них, поданный как «цена
Bravo», — выдумка.

**Не чинить склейку переклейкой при одинаковом штрихкоде и разной фасовке.**
Если цены сходятся, а описания фасовки разные — это дефект описания, а не
ошибка склейки.

## Долгосрочное решение

Скрейпинг — временная мера, и он нарушает пользовательские соглашения сетей.
Тот же фид, который сети уже отдают в Wolt и Birmarket, у них существует и
разработки не требует. Просить надо его. Это не снимет необходимость в
проверках — фид тоже меняется, — но снимет два класса поломок: «поменяли
разметку витрины» и «закрыли доступ по User-Agent».
