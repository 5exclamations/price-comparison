# Промпты для сборки приложения qiymət

Стек: **Flutter** (iOS + Android) и **FastAPI + PostgreSQL** поверх готового пайплайна сбора.

## Как этим пользоваться

Промпт №0 — это контекст. Положи его в `CLAUDE.md` (или `.cursorrules`) в корне репозитория,
и он подхватится автоматически в каждой сессии. Все остальные промпты вставляй по одному,
по порядку, доводя каждый до зелёных тестов перед следующим. Не склеивай их: агент начнёт
срезать углы там, где мы уже знаем, что углы срезать нельзя.

В промптах намеренно зашиты факты, которые я добыл замерами. Без них агент напишет
правдоподобный, но неверный код: возьмёт формат магазина за ценовую зону, сравнит 250 г
с килограммом, потеряет поиск по словам с турецкой İ.

## 0. Контекст проекта (в `CLAUDE.md`)

```
Проект qiymət — сравнение цен в супермаркетах Азербайджана.
Клиент: Flutter (iOS + Android). Бэкенд: FastAPI + PostgreSQL.
Языки интерфейса: азербайджанский (основной), русский, английский.
Валюта: манат (AZN). Все деньги в коде — целые числа в гяпиках. Никакого float.

Данные собирает готовый Python-пайплайн (папка pipeline/): шесть сетей —
Bazarstore, Bravo, Araz, SPAR, Neptun, Rahat. Схема в pipeline/schema.sql.

ФАКТЫ, ДОБЫТЫЕ ЗАМЕРАМИ. Не переизобретать, не спорить с ними:

1. Bravo не имеет единого прайса. Есть четыре ценовые зоны, и они НЕ совпадают
   с форматом магазина: в одной зоне лежат Superstore, Supermarket и Ekspress
   с одинаковыми ценами. Зона — измеренное поле stores.price_cluster, а не вывод
   из названия. Показывать цену Bravo без выбора магазина нельзя.
2. У Araz, SPAR, Neptun и Rahat цена одна на всю сеть (проверено на 8 и 3 филиалах).
   SPAR — премиальный формат Araz и держит тот же прайс.
3. Базовые цены сетей почти не отличаются: у 62% товаров, присутствующих минимум
   в трёх сетях, цена одинакова, медианная выгода от выбора сети 2.9%.
   ЦЕННОСТЬ ПРОДУКТА В АКЦИЯХ: там медианная выгода 26.7%, у четверти товаров
   больше 44%. Интерфейс должен вести к акциям, а не к таблице базовых цен.
4. Скидку считать от рынка, а не от ценника сети: настоящая скидка — это разница
   с медианой обычных, неакционных цен на тот же штрихкод в других сетях.
   4.6% акций имеют накрученную старую цену.
5. Товары склеиваются по EAN, отпечатку названия и похожести (символьные триграммы,
   порог 0.82, точность 96%). Часть склеек в карантине (products.quarantined = 1) —
   их НИКОГДА не показывать пользователю.
6. Весовые товары (unit_type = 'kg_bulk') не имеют штрихкода. Цена у них за килограмм.
   У Bazarstore весовые товары продаются вариантами «1 KG» и «250 gr» с
   пропорциональной ценой: сравнивать можно только килограмм с килограммом.

ЛОВУШКИ, НА КОТОРЫЕ Я УЖЕ НАСТУПИЛ:

- Турецкая İ. В JS и Dart 'İ'.toLowerCase() даёт 'i' + комбинирующий U+0307,
  и поиск «milka» перестаёт находить «MİLKA». Любая нормализация текста должна
  СНАЧАЛА заменять İ, I, Ə, Ö, Ü, Ç, Ş, Ğ, потом опускать регистр, потом сносить
  комбинирующие знаки через NFD.
- «qr» в азербайджанских названиях — это граммы (qram), а не что-то другое.
  Голый хвост «kq» без числа означает весовой товар. «7 Lİ», «10 LU» — упаковка из N штук.
- Одинаковый штрихкод не гарантирует одинаковую фасовку: сети врут в описаниях.
  Если цены сходятся, а описания фасовки разные — это дефект описания, не ошибка склейки.

СТИЛЬ КОДА:
- Деньги: int в гяпиках везде, форматирование только на границе UI.
- Никаких UPDATE по ценам. История цен — append-only таблица наблюдений.
- Каждое число, показанное пользователю, должно сопровождаться временем наблюдения.
```

## 1. Перенос схемы на PostgreSQL

```
В pipeline/schema.sql лежит рабочая схема SQLite на шесть таблиц: chains, stores,
products, store_items, price_observations, matches, match_queue, audit_log.
Прочитай её целиком, включая комментарии — там записаны решения, которые надо сохранить.

Сделай:
1. Каталог db/migrations/ с миграциями на Alembic. Первая миграция повторяет схему
   один в один на Postgres 16: SERIAL → GENERATED ALWAYS AS IDENTITY, TEXT-времена →
   timestamptz, CHECK-и сохранить.
2. Партиционирование price_observations по месяцам от observed_at. Через год при
   шести сетях там будут десятки миллионов строк, и запрос «текущая цена» не должен
   сканировать всё.
3. Материализованное представление current_prices вместо обычного: последнее
   наблюдение по каждому store_item_id. Обновлять CONCURRENTLY после каждого прогона
   сбора. Обычная вьюха с MAX(observed_at) на партиционированной таблице будет тормозить.
4. Индексы под три главных запроса: поиск товара по подстроке названия
   (pg_trgm + GIN), цены по product_id, лента акций (WHERE old_price IS NOT NULL).
5. Скрипт db/import_sqlite.py, который переливает существующий qiymet.db в Postgres
   пакетами по 5000 строк, с прогрессом и возможностью перезапуска с места обрыва.

Внимание: в SQLite UNIQUE (chain_id, store_id, chain_sku) не работал при store_id IS NULL,
поэтому там стоит отдельный уникальный индекс с COALESCE(store_id, 0). В Postgres
поведение NULL такое же — сохрани этот индекс, иначе появятся дубли позиций.

Проверка: после импорта количество строк в каждой таблице совпадает с SQLite,
запрос «цены на товар по всем сетям» на холодном кеше укладывается в 50 мс.
```

## 2. HTTP API на FastAPI

```
Подними FastAPI-приложение в api/ поверх схемы из шага 1. SQLAlchemy 2.0 async,
Pydantic v2, uvicorn.

Эндпоинты:

GET /v1/search?q=&store_id=&limit=&cursor=
  Поиск товара по названию и по штрихкоду. Нормализация запроса — та же, что
  описана в CLAUDE.md (İ сначала, потом регистр, потом NFD). Поиск по trigram-индексу.
  Возвращает товар, лучшую цену, количество сетей, где он есть, и флаг акции.
  Курсорная пагинация, не offset.

GET /v1/product/{id}?store_id=
  Карточка: цены по всем сетям, для Bravo — по зоне выбранного магазина.
  Каждая цена с полем observed_at. Если товар в карантине — 404, не показывать.

GET /v1/deals?store_id=&category=&min_discount=&limit=&cursor=
  Лента акций, отсортированная по НАСТОЯЩЕЙ скидке (от медианы неакционных цен
  на тот же штрихкод в других сетях), а не по заявленной. Логика уже написана
  в pipeline/honesty.py — перенеси её в SQL или в материализованное представление,
  пересчитываемое после каждого прогона сбора. Отдавай оба числа: заявленную скидку
  и настоящую, плюс флаг inflated, когда разница больше 15 процентных пунктов.

GET /v1/stores?lat=&lon=
  Магазины с расстоянием от точки. Для сетей с единой ценой возвращать одну
  синтетическую запись на сеть, а не список филиалов.

GET /v1/product/{id}/history?days=30
  История цены: точки для графика плюс события «акция началась / кончилась».

GET /v1/health
  Возраст самых свежих данных по каждой сети. Если сеть не обновлялась больше
  12 часов — статус degraded. Это нужно клиенту, чтобы честно писать «данные устарели».

Требования:
- Ответы кешировать в Redis на 5 минут, ключ включает store_id.
- ETag и Cache-Control на всех GET.
- Все цены в JSON — целые гяпики, поле называется price_minor. Клиент форматирует сам.
- OpenAPI-схема должна собираться, к ней сгенерируем модели для Flutter.

Тесты: pytest + httpx на каждый эндпоинт, включая пустой результат, карантинный товар
и несуществующий store_id.
```

## 3. Подписки на товар и пуш-уведомления

```
Пользователь подписывается на товар и получает пуш, когда цена падает.
Это главная удерживающая механика — без неё приложение открывают один раз.

Бэкенд:
- Таблицы users (анонимный id устройства достаточно для первой версии, без регистрации),
  device_tokens, watches (user_id, product_id, store_id, target_price_minor nullable).
- Воркер, который после каждого прогона сбора сравнивает новые наблюдения с предыдущими
  и ставит в очередь уведомления. Не опрашивать в цикле, а брать дельты из
  price_observations, как в pipeline/history.py.
- Правила отправки: цена упала минимум на 5% ИЛИ опустилась ниже target_price.
  Не больше одного пуша в сутки на пользователя по одному товару.
  Тихие часы 23:00–08:00 по Баку (Asia/Baku, UTC+4) — копить и слать утром.
- Отправка через Firebase Cloud Messaging, батчами, с обработкой невалидных токенов.

Текст уведомления на языке пользователя, коротко и с числами:
«Papia tualet kağızı 32 li — 13.99 ₼ в Bravo вместо 34.69. Дешевле рынка на 60%.»

Не отправлять уведомление, если скидка накрученная (см. inflated из /v1/deals).
Смысл продукта в том, чтобы не врать, а не в том, чтобы слать побольше пушей.

Тесты: воркер на подготовленном наборе дельт даёт ровно ожидаемый список уведомлений,
тихие часы соблюдаются, дедупликация работает.
```

## 4. Flutter: каркас и дизайн-система

```
Создай Flutter-приложение в app/. Требования: Flutter 3.24+, Dart 3, Material 3,
поддержка светлой и тёмной темы, локализации az (основная), ru, en.

Архитектура:
- riverpod для состояния, go_router для навигации, dio + retrofit для сети,
  freezed + json_serializable для моделей (генерировать из OpenAPI-схемы шага 2),
  drift для локального кеша.
- Слои: data (api, cache) → domain (модели, use cases) → presentation.
  Никаких вызовов dio из виджетов.

Дизайн-система в lib/design/:
- Токены: цвета, типографика, отступы по шкале 4. Никаких магических чисел в виджетах.
- Цена — отдельный виджет PriceText, принимает int в гяпиках, форматирует по локали,
  умеет показывать зачёркнутую старую цену. Нигде больше не форматировать деньги.
- Цвета для «дешевле всех» и «дороже всех» должны различаться не только цветом,
  но и весом шрифта: дальтоников в Азербайджане столько же, сколько везде.
- Шрифт обязан корректно рисовать ə, ı, ğ, ş, ç, ö, ü. Проверь на строке
  «Çuğundur, göbələk, şəkər tozu, ət və südlü məhsullar».

Экраны-заглушки и роуты: /onboarding, /search, /product/:id, /deals, /list, /settings.
Нижняя навигация: Поиск, Выгоды, Список, Настройки.

Утилита normalizeAz(String) в lib/core/text.dart. Реализация строго в таком порядке:
заменить İ→i, I→i, Ə→a, Ö→o, Ü→u, Ç→c, Ş→s, Ğ→g; затем toLowerCase();
затем NFD и удаление диакритики U+0300–U+036F; затем ə→a, ı→i и остальные строчные.
Юнит-тест обязателен: normalizeAz('MİLKA') == 'milka', normalizeAz('ÇUĞUNDUR') == 'cugundur'.
Если сделать toLowerCase() первым, поиск сломается на всех словах с İ.
```

```
Экран /list — список покупок, и он же ответ на вопрос «куда ехать».
```

## 9. Сбор чеков через e-kassa

```
Это отдельный источник данных, точнее скрейпинга, и его больше ни у кого нет.

В Азербайджане все кассы фискальные, на каждом чеке QR со ссылкой на портал
e-kassa.gov.az, где открывается состав чека с позициями и ценами.

Сделай:
- Экран сканирования чека: пользователь наводит камеру на QR (mobile_scanner),
  приложение читает ссылку и отправляет её на бэкенд.
- Бэкенд разбирает страницу чека: магазин, время, позиции, цены, итог.
  Складывает в отдельную таблицу receipts / receipt_items, а не сразу в
  price_observations: это другой источник, source = 'receipt'.
- Валидация: если чек уже загружен (по номеру), не дублировать. Если магазин
  не из наших сетей — всё равно сохранить, это расширяет покрытие бесплатно.
- Начислять пользователю баллы за загруженный чек.

Юридическая часть: это персональные данные пользователя. Нужен явный экран
согласия с понятным текстом, возможность отозвать согласие и удалить свои чеки,
и обезличивание перед использованием в общей аналитике. Закон Азербайджанской
Республики «О персональных данных» — сослаться в политике конфиденциальности.
```

## 10. Приёмка и защита от тихих поломок

```
Напиши набор проверок, которые гоняются в CI и после каждого прогона сбора.
Задача не «покрыть код тестами», а поймать ровно те поломки, которые уже случались.

9. Юнит-тест normalizeAz на İ, Ə, Ğ, Ş и на смеси латиницы с кириллицей.

Любая упавшая проверка блокирует деплой. Отдельно: если проверки 5–8 падают
```

## 11. Деплой

```

- Мониторинг: healthcheck из /v1/health в uptime-монитор, алерт в Telegram, когда
  сеть не обновлялась 12 часов или прогон упал.
```

## Чего сознательно нет в этих промптах

Регистрации и профиля — на старте хватит анонимного id устройства, регистрация
режет конверсию, а ничего от пользователя нам пока не нужно.

Рекомендаций и персонализации — сортировать по честной выгоде важнее, чем угадывать
вкусы, и это работает с первого дня без данных о поведении.

Монетизации — сначала надо получить работающие данные и удержание. Когда они будут,
самый очевидный путь не реклама, а продажа сетям аналитики по ценам конкурентов:
за это категорийные менеджеры платят живыми деньгами, и история цен у нас уже копится.

## Что нужно от тебя, а не от агента

Эти вещи агент добыть не может, их надо принести.

**Домен и сервер.** Без домена Caddy не выпустит сертификат. Нужен доступ к VPS

формат ответа портала e-kassa угадан, и подстроить надо один метод.

**Решение про скрейпинг.** До деплоя это была работа в стол. После — публичный
