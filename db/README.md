# db/ — схема qiymət на Postgres

Перенос рабочей SQLite-схемы `pipeline/schema.sql` на Postgres 16: миграции
Alembic, помесячные секции истории цен, материализованная витрина текущих цен
и разовый перелив данных из `qiymet.db`.

```bash
pip install -r db/requirements.txt
export DATABASE_URL=postgresql+psycopg://qiymet@localhost:5432/qiymet

cd db && alembic upgrade head && cd ..
python3 db/import_sqlite.py --sqlite pipeline/qiymet.db
```

## Миграции

| ревизия | что делает |
|---|---|
| `0001` | схема один в один: 8 таблиц, CHECK-и, индексы, комментарии |
| `0002` | помесячные секции `price_observations` + функции их создания |
| `0003` | `current_prices` как матвьюха, `product_prices`, `product_prices_public` |
| `0004` | индексы под поиск, цены по товару и ленту акций |

`alembic.ini` намеренно **только ASCII**. configparser читает его в кодировке
локали, и один русский байт роняет alembic под `LANG=C` — то есть вslim-образе
на деплое. Файлы миграций это не касается: исходники Python по умолчанию UTF-8.

Строка подключения живёт в `DATABASE_URL`, в `alembic.ini` её нет, чтобы пароль
от прода не уехал в git.

## Что изменилось против SQLite и почему

Сознательные отступления от «один в один» — их четыре, остальное перенесено дословно.

**1. Первичный ключ `price_observations` стал составным.** Было `(id)`, стало
`(id, observed_at)`. Postgres требует, чтобы ключ секционирования входил в
первичный ключ. На `price_observations` никто не ссылается внешним ключом, так
что практических последствий нет.

**2. `price_observations.id` — `bigint`, а не `integer`.** Таблица append-only и
растёт вечно. В SQLite `INTEGER` и так 64-битный, так что это скорее
восстановление исходного типа, чем отступление.

**3. Флаги 0/1 остались числами, а не стали `boolean`.** `products.quarantined`,
`price_observations.available`, `audit_log.quarantined` — это `smallint` с
`CHECK (x IN (0,1))`. Родной для Postgres тип тут `boolean`, но в пайплайне и в
CLAUDE.md записано `quarantined = 1`, и такие запросы должны продолжать работать
без правок.

**4. `current_prices.is_promo` — наоборот, стал `boolean`.** Здесь можно: ни
пайплайн, ни витрина это поле не читают, менять нечего.

Что перенесено дословно и трогать нельзя:

- **Уникальный индекс `idx_si_sku` с `COALESCE(store_id, 0)`.** В Postgres, как и
  в SQLite, NULL не равен NULL, поэтому `UNIQUE (chain_id, store_id, chain_sku)`
  не ловит дубли у сетей с единой ценой, где `store_id` пустой. Порядок колонок
  менять нельзя: `pipeline.py` делает
  `ON CONFLICT (chain_id, COALESCE(store_id, 0), chain_sku)`, а Postgres выводит
  целевой индекс по точному совпадению выражений. У Postgres 15+ есть
  `UNIQUE NULLS NOT DISTINCT`, который решил бы ту же задачу без функционального
  индекса, но сломал бы этот `ON CONFLICT`.
- Все CHECK-и, включая списки допустимых значений `price_model`, `ean_kind`,
  `method`, `status`.
- Деньги: `integer` в гяпиках. Даже `price_azn` в витрине даёт `numeric`, а не
  float — литерал `100.0` в Postgres имеет тип `numeric`.

## Секции истории цен

`price_observations` секционирована по месяцам от `observed_at`, **границы в UTC**
(иначе они поехали бы при смене `TimeZone` у сессии).

Держать секции «на вырост» — на том же cron, что и сбор:

```cron
0 */3 * * *  psql -c "SELECT ensure_price_partitions_ahead(3)"
```

Секция `price_observations_default` — страховка от `INSERT` с датой вне известных
секций: без неё ночной прогон упал бы первого числа месяца. **Она обязана быть
пустой.** Непустая означает, что `ensure_price_partitions_ahead()` не вызывается,
и вдобавок замедляет создание новых секций: Postgres сканирует DEFAULT под
`ACCESS EXCLUSIVE`, проверяя, что там нет строк из нового диапазона.

```sql
SELECT * FROM price_partitions_health;   -- тревога, если у default approx_rows > 0
```

## current_prices

Матвьюха, а не обычная вьюха. На секционированной таблице в десятки миллионов
строк старый `join` на `GROUP BY store_item_id MAX(observed_at)` означал бы
агрегат по всей истории на каждый запрос «текущая цена».

Собирается через `DISTINCT ON (store_item_id) ... ORDER BY store_item_id,
observed_at DESC, id DESC`. Добивание по `id DESC` не косметика: пайплайн ставит
время с точностью до секунды, два наблюдения могут попасть в одну секунду, и
старый `MAX`-join вернул бы на такую позицию две строки. С двумя строками
невозможен уникальный индекс, а без него не работает `REFRESH CONCURRENTLY`.

После каждого прогона сбора:

```sql
SELECT refresh_current_prices();
```

`CONCURRENTLY` не блокирует читателей — витрина продолжает отвечать, пока
матвьюха пересобирается. Функция сама проверяет `relispopulated` и делает первый
refresh неконкурентным, если матвьюха создана `WITH NO DATA`.

## Карантин

`product_prices` оставлена один в один с SQLite и карантин **не фильтрует**.
Витрина обязана читать `product_prices_public` — то же самое, но без склеек с
`quarantined = 1`. Правило «карантинные товары не показывать никогда» не должно
держаться на памяти прикладного разработчика.

## Поиск по названию

```sql
SELECT id, name FROM products
WHERE qiymet_norm(name) LIKE '%' || qiymet_norm($1) || '%'
  AND quarantined = 0;
```

Обёртка `qiymet_norm()` обязательна с обеих сторон — индекс построен по
выражению, и запрос должен совпадать с ним выражение в выражение.

Внутри функции сначала `translate()` азербайджанских букв, и только потом
`lower()`. Обратный порядок ломает поиск: `lower('İ')` в UTF-8 даёт
`'i' + U+0307` (комбинирующая точка), и «milka» перестаёт находить «MİLKA».

После NFD двойники сворачиваются **ещё раз** (миграция `0009`). Без этого
функция не идемпотентна: «Ё» на первом шаге двойником не считается, NFD
раскладывает её в «е» + U+0308 и оставляет кириллическую «е», а второй проход
свернул бы её в латинскую «e». Клиент нормализует запрос у себя, сервер
применяет функцию ещё раз — и «мёд» переставал находить «Мёд». Проверка
идемпотентности стоит прямо внутри миграции: если условие сломать, `alembic
upgrade` не пройдёт.

Клиентская `normalizeAz` (`app/lib/core/text.dart`) обязана давать тот же
результат посимвольно. Сверено на живой базе: `Молоко` → `мoлoko`,
`Шоколад` → `шokoлaд`, `Сахар` → `caxap`, `Ёж` → `eж`, `Кока-Кола Zero 330 ml`
→ `koka-koлa zero 330 ml`. Сторожится тестом «смесь латиницы с кириллицей».

Триграммы работают от 3 символов. На более коротком запросе планировщик уйдёт в
seq scan — это нормально и ожидаемо.

## Перелив из SQLite

```bash
python3 db/import_sqlite.py --sqlite pipeline/qiymet.db   # перелить
python3 db/import_sqlite.py --verify                      # сверить счётчики
python3 db/import_sqlite.py --restart                     # снести и начать заново
```

Пакеты по 5000 строк (`--batch`). Перезапуск с места обрыва: в
`_import_progress` лежит водяной знак по каждой таблице, и **пакет строк со
сдвигом водяного знака пишутся в одной транзакции**. Обрыв откатывает и то и
другое, после перезапуска работа продолжается ровно с последнего
зафиксированного id — без дублей, дыр и `ON CONFLICT`.

Времена из SQLite читаются как **UTC** (там они от `datetime('now')`). Иначе вся
история цен уехала бы на 4 часа, а «время наблюдения» на витрине стало бы
враньём.

После успешной сверки `_import_progress` можно удалить.

## Проверено замерами

Импорт 151 208 строк из `qiymet.db` — 4.1 с, все восемь таблиц сошлись построчно.
Перезапуск проверен `kill -9` в середине: 25 700 строк зафиксированы, водяной
знак ровно на них, продолжение добежало до полного совпадения.

На **20 053 191 наблюдении** (годовая история, 14 секций), холодный
`shared_buffers`:

| запрос | время |
|---|---|
| цены на товар по всем сетям | **18,9 мс** |
| поиск по подстроке названия | 14,2 мс |
| лента акций, топ-50 | 23,9 мс |

Запрос цен идёт планом `Index Only Scan` по `idx_si_product_covering`
(`Heap Fetches: 0`) и точечным `Index Scan` в матвьюху — 32 буфера на весь запрос.

Тот же запрос через **обычную** вьюху с `MAX(observed_at)`, как было в SQLite, на
тех же данных: **1842 мс**, причём на тёплом кеше. Разница в 97 раз — это и есть
цена решения из пункта 3.

`REFRESH MATERIALIZED VIEW CONCURRENTLY` на 20 млн строк занимает **29 с**. Для
прогона раз в 2–4 часа это приемлемо, но при росте истории за этим стоит следить:
`CONCURRENTLY` читателей не блокирует, так что витрина всё это время отвечает.

Оговорка про «холодный кеш»: очищается `shared_buffers` (перезапуском Postgres),
страничный кеш macOS — нет, для него нужен `sudo purge`. На сервере с прогретым
page cache цифры будут не хуже.

Цифры сняты на Postgres 17 (локально не было 16). Всё используемое —
identity-колонки, секционирование RANGE, `INCLUDE`-индексы,
`REFRESH CONCURRENTLY`, `gin_trgm_ops` — есть начиная с Postgres 14, так что на
16 поведение то же.

## Границы секций — в UTC

Это всплыло на генерации тестовых данных и стоит запомнить. Границы секций
заданы в UTC. Пайплайн пишет `now()` / `datetime('now')`, то есть тоже UTC, и
проблемы не создаёт. Но любой писатель, который сформирует время как локальную
полночь (`date_trunc('month', ...)::timestamptz` в сессии с `TimeZone=Asia/Baku`),
получит 31 июля 20:00 UTC вместо 1 августа — и первые четыре часа месяца уедут в
соседнюю секцию, а у самой ранней — в DEFAULT.

Ровно это и произошло при генерации: 57 459 строк осели в DEFAULT, и
`price_partitions_health` их показала. Штатный слив DEFAULT:

```sql
CREATE TEMP TABLE stray AS SELECT * FROM price_observations_default;
TRUNCATE price_observations_default;
SELECT ensure_price_partition('2025-07-01'::date);
INSERT INTO price_observations
    (id, store_item_id, price, old_price, promo_until, available, observed_at, source)
OVERRIDING SYSTEM VALUE
SELECT id, store_item_id, price, old_price, promo_until, available, observed_at, source
FROM stray;
```

`OVERRIDING SYSTEM VALUE` здесь обязателен: `id` объявлен
`GENERATED ALWAYS AS IDENTITY`, и без него Postgres откажется принимать явные
значения.
